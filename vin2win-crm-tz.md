# ТЗ: VIN2WIN CRM — колл-центр и учёт звонков

**Заказчик:** VIN2WIN
**Домен:** `vin2win.online`
**Исполнитель:** Claude Code (полный цикл — от инициализации репозитория до деплоя на VPS)
**Статус этапа:** MVP-1 «Интерфейс + аккаунты + каркас телефонии»

---

## 0. Прежде чем начать — критично

### 0.1. Секреты

Все креды (VPS root, PostgreSQL, будущие ключи МТС Exolve) передаются отдельно и **никогда** не попадают в репозиторий.

- Все значения — только в `.env` (локально) и в переменных окружения на сервере.
- В репозиторий кладётся **только** `.env.example` с пустыми значениями.
- `.env`, `*.pem`, `*.key` — в `.gitignore` с первого коммита.
- Секреты не логируются, не попадают в сообщения об ошибках и не выводятся в консоль.

> **Отдельно к заказчику:** пароли VPS и БД были отправлены в переписке в открытом виде. Их нужно сменить **до** начала работ: сменить пароль root на VPS (или, лучше, отключить парольный вход и перейти на SSH-ключ), сменить пароль пользователя `gen_user` в PostgreSQL. Дальше работать уже с новыми значениями.

### 0.2. Что делаем на этом этапе, а что нет

**Делаем:**
- Полностью рабочий UI: тёмная и светлая темы, десктоп и мобильные.
- Аутентификация, роли, админский кабинет, создание кабинетов менеджеров.
- Схема БД под звонки и подключение к PostgreSQL.
- Рабочий раздел «Звонки» со списком, фильтрами, карточкой звонка, дашбордом статистики.
- Realtime-обновление статистики: как только звонок завершён — он появляется в CRM без перезагрузки страницы.
- Адаптер телефонии с полностью описанным интерфейсом + **mock-провайдер**, генерирующий реалистичные события звонков. На нём разрабатывается и демонстрируется вся логика.
- Готовый эндпоинт вебхука Exolve и клиент к их API — но **выключенные** по фиче-флагу.

**НЕ делаем на этом этапе:**
- Реальное подключение к МТС Exolve (заказчик ещё не зарегистрирован — ключей нет).
- Транскрибацию звонков. В схеме БД и в UI закладываем места под неё, но реализацию откладываем.
- Сделки, воронки, e-mail, задачи, интеграцию с каталогом vin2win.ru.

Архитектура должна быть такой, чтобы переход с mock на Exolve был заменой одной переменной окружения, а не переписыванием.

## 1. Стек

Выбран так, чтобы совпадать с основным сайтом vin2win (тот же Tailwind-токен-слой из `globals.css`) и чтобы одному разработчику было реально его поддерживать.

| Слой | Технология | Почему |
|---|---|---|
| Фреймворк | **Next.js 15+, App Router, TypeScript (strict)** | SSR для быстрых таблиц, API-routes в том же проекте — не нужен отдельный бэкенд |
| Стили | **Tailwind CSS v4 + CSS-переменные** | Палитра уже описана токенами, переносится один в один |
| Компоненты | **shadcn/ui** (Radix под капотом) | Доступность из коробки, полностью кастомизируется под токены, не выглядит как чужой UI-кит |
| БД | **PostgreSQL** (внешний хост, уже выделен) | — |
| ORM | **Prisma** | Миграции, типизация, читаемая схема |
| Auth | **Auth.js (NextAuth v5), credentials provider, JWT-сессия в httpOnly cookie** | Свои логины/пароли, без внешних провайдеров |
| Пароли | **argon2id** (`@node-rs/argon2`) | — |
| Валидация | **Zod** + `react-hook-form` | Одна схема на клиент и сервер |
| Данные на клиенте | **TanStack Query** | Кэш, инвалидация, оптимистичные апдейты |
| Realtime | **SSE** (`/api/events/stream`) + **Postgres LISTEN/NOTIFY** | Проще WebSocket, проходит через nginx, не требует Redis |
| Графики | **Recharts** | Легко темизируется под CSS-переменные |
| Таблицы | **TanStack Table** (headless) | Сортировка, пагинация, свои стили |
| Даты | **date-fns** + `ru` локаль | — |
| Тесты | **Vitest** (unit) + **Playwright** (e2e по ключевым сценариям) | — |
| Логи | **pino** | Структурированные JSON-логи |
| Деплой | **Docker + docker compose + nginx + certbot** | — |

Пакетный менеджер: **pnpm**. Линт: **ESLint + Prettier**, прогон в pre-commit через **husky + lint-staged**.

## 2. Дизайн

### 2.1. Референсы

За основу берутся три макета (заказчик указал их как эталон композиции и плотности информации):

1. **CRM Call Center Element (Figma Community)** — общая структура рабочего места оператора.
2. **Call Center Dashboard (Figma Community)** — дашборд, метрики, графики нагрузки.
3. **CRM Woorkroom (Figma Community)** — навигация, карточки, типографика, сетка.

Из них берём **структуру и композицию**: расположение сайдбара, плотность таблиц, набор и иерархию метрик на дашборде, паттерн карточки звонка. Цвета, шрифты, скругления, тени — **полностью наши**. Копирование пиксель-в-пиксель не требуется и не нужно: результат должен читаться как продукт VIN2WIN, а не как чужой шаблон, перекрашенный в зелёный.

**Правила использования цвета:**

- Зелёный — это **бренд и успех**, а не «любой акцент». Не красить им всё подряд: в интерфейсе колл-центра зелёный должен означать «принято / успешно / целевое действие».
- Статусы звонков имеют собственную семантику: успешный — `--success`, пропущенный — `--destructive`, в процессе — жёлтый бейдж `#ffd800`, исходящий без ответа — нейтральный `--text-muted`.
- Жёлтый бейдж `#ffd800` — редкий, только на «требует внимания». Если он на каждой строке, он перестаёт работать.
- Никаких новых hex-значений в компонентах. Только токены. Если нужного оттенка нет — добавить токен в `globals.css` и согласовать.

### 2.3. Типографика

Если на основном сайте vin2win уже используется конкретная пара шрифтов — взять её и не изобретать. Если нет, дефолт для этого проекта:

- **Интерфейс и данные:** `Inter` (variable), tabular-nums для всех числовых колонок и таймеров.
- **Заголовки экранов и крупные метрики:** `Unbounded` в весе 700/800 — уже используется в презентационных материалах VIN2WIN, даёт узнаваемость. Применять сдержанно: только H1 экрана и цифры KPI на дашборде.

Шкала: 12 / 13 / 14 / 16 / 20 / 28 / 40. Базовый размер интерфейса — 14px, в таблицах допускается 13px.

Все длительности звонков, номера телефонов и денежные значения — моноширинные цифры (`font-variant-numeric: tabular-nums`), иначе колонки «пляшут».

### 2.4. Темы

- Три режима: `light`, `dark`, `system`.
- Переключатель — в шапке и в настройках профиля.
- Хранение выбора: `localStorage` + cookie, чтобы SSR отдавал сразу правильную тему **без вспышки** (инлайновый скрипт в `<head>`, ставящий класс на `body` до гидратации).
- Реализация через класс на `body` (`theme-light` / `theme-dark`), как в существующем `globals.css`.
- По умолчанию для новых пользователей — `system`.

### 2.5. Адаптив

Брейкпоинты: `sm 640 / md 768 / lg 1024 / xl 1280`.

- **≥1024px** — полноценный рабочий стол: постоянный сайдбар, таблицы в полном виде.
- **768–1023px** — сайдбар сворачивается в иконки, таблицы теряют второстепенные колонки.
- **<768px (телефон менеджера)** — приоритетный сценарий, не «остаточный»:
  - нижняя навигация из 4 пунктов: Звонки, Дашборд, Контакты, Профиль;
  - таблица звонков превращается в **список карточек**, а не в горизонтально скроллящуюся таблицу;
  - в карточке: имя/номер, направление (иконка), статус, длительность, время, кнопка «Позвонить» (`tel:`);
  - фильтры — в bottom-sheet, не в выпадашках;
  - все интерактивные элементы — минимум 44×44px;
  - формы — одноколоночные, поля ввода телефона с `inputmode="tel"`.

### 2.6. Качество исполнения (обязательный минимум)

- Видимый фокус клавиатуры на всех интерактивных элементах.
- Контраст текста — не ниже WCAG AA (4.5:1 для основного текста). Для `#15803d` с белым текстом — проверено, проходит; `#16a34a` с белым на мелком тексте — не использовать.
- `prefers-reduced-motion` — уважается, все анимации отключаются.
- Скелетоны при загрузке, а не спиннер на весь экран.
- Осмысленные пустые состояния: не «Нет данных», а «Звонков за сегодня ещё не было» + подсказка, что делать.
- Ошибки говорят, что произошло и что делать. Без извинений и без технических кодов в лицо пользователю.
- Все подписи — в предложенческом регистре, активным залогом: «Создать менеджера», не «Создание менеджера».
- Интерфейс на русском. Строки вынести в один словарь (`lib/i18n/ru.ts`), чтобы позже можно было добавить язык.

## 3. Роли и доступ

### 3.1. Роли

| Роль | Возможности |
|---|---|
| `ADMIN` | Всё. Создаёт, редактирует, блокирует аккаунты менеджеров. Видит звонки всех. Видит сводную статистику по компании и по каждому менеджеру. Доступ к настройкам, аудит-логу, настройкам телефонии. |
| `MANAGER` | Видит **только свои** звонки и свою статистику. Редактирует свой профиль и результат звонка. Не видит других менеджеров и настройки системы. |

Заложить в схему роль `SUPERVISOR` (видит команду, но не настройки) — на будущее, в UI пока не выводить.

### 3.2. Правила

- Изоляция данных — **на уровне сервера**, а не через скрытие кнопок. Каждый запрос данных фильтруется по `session.user.id`, если роль не `ADMIN`.
- Проверка роли — в едином хелпере `requireRole()`, вызываемом в каждом server action и API-роуте. Нет проверки — нет роута.
- Первый администратор создаётся сид-скриптом `pnpm db:seed`, логин и стартовый пароль берутся из `.env`. При первом входе система **обязывает** сменить пароль.
- Публичной регистрации нет. Менеджер попадает в систему только через админа.

### 3.3. Сценарий создания менеджера

1. Админ → «Пользователи» → «Создать менеджера».
2. Форма: ФИО, e-mail (логин), телефон, внутренний номер SIP/добавочный (поле на будущее, необязательное), роль, часовой пояс.
3. Система генерирует одноразовый пароль **или** ссылку-приглашение с токеном на 72 часа. Выбрать вариант с приглашением как основной, одноразовый пароль — запасной (на случай, если почта не настроена — тогда админ просто копирует пароль и передаёт лично).
4. Менеджер по ссылке задаёт свой пароль и входит.
5. Админ может: деактивировать аккаунт (без удаления — звонки остаются в истории и в статистике), сбросить пароль, изменить роль.
6. Удаление аккаунта — **мягкое** (`deletedAt`). Жёсткое удаление не предусмотрено.

### 3.4. Безопасность

- Пароли: argon2id, минимум 10 символов, проверка на утечки не требуется.
- Rate limit на вход: 5 попыток / 15 минут на связку IP+логин, дальше блокировка на 15 минут.
- Сессия: httpOnly + Secure + SameSite=Lax cookie, срок 12 часов, скользящее продление.
- CSRF-защита на всех мутациях (Auth.js даёт из коробки, проверить для кастомных роутов).
- Все админские действия пишутся в `AuditLog`.
- Заголовки: `X-Robots-Tag: noindex`, CSP, HSTS.

## 4. Модель данных (Prisma)

Схема ниже — целевая. Поля под транскрибацию создаются сразу, заполняются позже.

```prisma
enum Role {
  ADMIN
  SUPERVISOR
  MANAGER
}

enum CallDirection {
  INBOUND
  OUTBOUND
}

enum CallStatus {
  RINGING      // идёт дозвон
  IN_PROGRESS  // разговор
  COMPLETED    // завершён с разговором
  MISSED       // входящий без ответа
  NO_ANSWER    // исходящий без ответа
  BUSY
  FAILED
  CANCELED
}

enum CallOutcome {   // результат, ставит менеджер вручную
  NEW
  INTERESTED
  CALLBACK
  REFUSED
  WRONG_NUMBER
  DEAL
  SPAM
}

model User {
  id            String    @id @default(cuid())
  email         String    @unique
  name          String
  phone         String?
  extension     String?   @unique   // внутренний номер в АТС
  passwordHash  String?
  role          Role      @default(MANAGER)
  isActive      Boolean   @default(true)
  mustChangePassword Boolean @default(false)
  theme         String    @default("system")
  timezone      String    @default("Europe/Moscow")
  lastLoginAt   DateTime?
  createdById   String?
  createdBy     User?     @relation("UserCreator", fields: [createdById], references: [id])
  createdUsers  User[]    @relation("UserCreator")
  deletedAt     DateTime?
  createdAt     DateTime  @default(now())
  updatedAt     DateTime  @updatedAt

  calls         Call[]
  invites       Invite[]
  auditLogs     AuditLog[]

  @@index([role, isActive])
}

model Invite {
  id         String   @id @default(cuid())
  userId     String
  user       User     @relation(fields: [userId], references: [id])
  tokenHash  String   @unique
  expiresAt  DateTime
  usedAt     DateTime?
  createdAt  DateTime @default(now())
}

model Contact {
  id          String   @id @default(cuid())
  phoneE164   String   @unique          // единый формат +7XXXXXXXXXX
  name        String?
  company     String?
  note        String?
  isBlocked   Boolean  @default(false)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  calls       Call[]

  @@index([name])
}

model Call {
  id             String        @id @default(cuid())
  externalId     String?       @unique   // id звонка в Exolve, для идемпотентности
  provider       String        @default("mock")
  direction      CallDirection
  status         CallStatus
  outcome        CallOutcome   @default(NEW)

  fromNumber     String
  toNumber       String
  contactId      String?
  contact        Contact?      @relation(fields: [contactId], references: [id])

  userId         String?                 // менеджер
  user           User?         @relation(fields: [userId], references: [id])

  startedAt      DateTime
  answeredAt     DateTime?
  endedAt        DateTime?
  waitSeconds    Int?                    // до ответа
  durationSeconds Int          @default(0)  // длительность разговора
  billSeconds    Int?

  recordingUrl   String?
  recordingReady Boolean       @default(false)

  transcript     CallTranscript?

  comment        String?
  tags           String[]      @default([])

  rawPayload     Json?                   // сырой ответ провайдера, для отладки
  createdAt      DateTime      @default(now())
  updatedAt      DateTime      @updatedAt

  @@index([userId, startedAt])
  @@index([status, startedAt])
  @@index([startedAt])
  @@index([direction, startedAt])
}

model CallTranscript {
  id          String   @id @default(cuid())
  callId      String   @unique
  call        Call     @relation(fields: [callId], references: [id], onDelete: Cascade)
  status      String   @default("PENDING")  // PENDING | PROCESSING | READY | FAILED
  language    String   @default("ru")
  fullText    String?
  segments    Json?    // [{speaker, startMs, endMs, text}]
  summary     String?
  provider    String?
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
}

model AuditLog {
  id         String   @id @default(cuid())
  actorId    String?
  actor      User?    @relation(fields: [actorId], references: [id])
  action     String   // user.create, user.deactivate, call.outcome.update, settings.update
  entityType String
  entityId   String?
  meta       Json?
  ip         String?
  userAgent  String?
  createdAt  DateTime @default(now())

  @@index([actorId, createdAt])
  @@index([entityType, entityId])
}

model Setting {
  key       String   @id
  value     Json
  updatedAt DateTime @updatedAt
}
```

**Правила работы с данными:**

- Все номера телефонов нормализуются в E.164 (`+7XXXXXXXXXX`) **на входе**, через `libphonenumber-js`. В UI показываются форматированно: `+7 (999) 123-45-67`.
- Все временные метки хранятся в UTC, отображаются в таймзоне пользователя.
- При поступлении звонка контакт находится по `phoneE164` или создаётся автоматически.
- `externalId` — ключ идемпотентности: повторный вебхук от Exolve не создаёт дубль, а обновляет запись (`upsert`).

## 5. Экраны

### 5.1. Общая оболочка

- **Сайдбар** (десктоп): логотип VIN2WIN, разделы, внизу — блок пользователя (аватар-инициалы, имя, роль) с меню «Профиль / Тема / Выход».
- **Шапка**: заголовок экрана, глобальный поиск по номеру и имени контакта, переключатель темы, индикатор realtime-соединения (маленькая точка: зелёная — подключено, серая — переподключение), колокольчик уведомлений.
- **Нижняя навигация** (мобильные): Звонки / Дашборд / Контакты / Профиль.

Разделы для `MANAGER`: Дашборд, Звонки, Контакты, Профиль.
Разделы для `ADMIN`: то же + Пользователи, Аналитика, Телефония, Аудит, Настройки.

### 5.2. `/login`

Минималистичный экран. Логотип, поля e-mail и пароль, кнопка «Войти». Ошибки — конкретные, но без раскрытия, существует ли пользователь: «Неверный e-mail или пароль». Отдельная страница `/invite/[token]` для задания пароля по приглашению.

### 5.3. `/` — Дашборд

**Для менеджера** (за выбранный период, по умолчанию «Сегодня»):

- 4 KPI-карточки: Всего звонков · Принято · Пропущено · Средняя длительность.
- График звонков по часам (столбцы, разделение входящие/исходящие).
- Круговая диаграмма по результатам (`CallOutcome`).
- Блок «Последние звонки» — 5 строк, обновляется в реальном времени.
- Блок «Нужно перезвонить» — звонки со статусом `MISSED` и результатом `CALLBACK`, отсортированные по давности. Это главный рабочий блок менеджера, он должен быть заметен.

**Для админа** — то же плюс:

- Разрез по менеджерам: таблица «Менеджер · Звонков · Принято · Пропущено · Ср. длительность · Общее время в разговоре».
- Переключатель «Вся компания / конкретный менеджер».
- Метрика скорости ответа (среднее `waitSeconds`) и доля пропущенных.

Период: Сегодня / Вчера / 7 дней / 30 дней / Произвольный диапазон.

### 5.4. `/calls` — Журнал звонков

Основной рабочий экран.

**Колонки:** статус (иконка + цвет) · направление · номер и имя контакта · менеджер (только для админа) · начало · ожидание · длительность · результат · запись (иконка плеера) · действия.

**Фильтры:** период, направление, статус, результат, менеджер (админ), поиск по номеру/имени, «есть запись», «есть комментарий».

**Поведение:**
- Пагинация серверная, по 50 записей, курсорная.
- Сортировка по времени начала (по умолчанию — новые сверху).
- Новый завершённый звонок **вставляется в начало списка в реальном времени** с короткой подсветкой строки (зелёный `--brand-soft` фон, затухание за 2 секунды; при `prefers-reduced-motion` — без анимации).
- Клик по строке открывает боковую панель (drawer) с карточкой звонка, URL меняется на `/calls/[id]` — ссылку можно переслать.
- Экспорт отфильтрованного списка в CSV/XLSX (только админ).

**Карточка звонка (drawer):**
- Шапка: номер, имя контакта, направление, статус, длительность.
- Таймлайн: начало → ответ → завершение с точным временем.
- Аудиоплеер записи (когда доступна): play/pause, перемотка, скорость 1x/1.5x/2x, скачивание.
- Блок «Транскрипция» — на этом этапе всегда в состоянии «Транскрипция будет доступна после подключения телефонии». Место в вёрстке заложено под текст с разбивкой по спикерам.
- Результат звонка — селект, менеджер меняет сразу из карточки.
- Комментарий — textarea с автосохранением.
- Теги.
- История звонков этого же контакта — список ниже.

### 5.5. `/contacts` — Контакты

Список номеров, с которыми были звонки. Поиск, имя, компания, заметка, количество звонков, последний звонок. Карточка контакта = вся история общения. Возможность отметить номер как заблокированный/спам.

### 5.6. `/admin/users` — Пользователи *(только ADMIN)*

- Таблица: имя, e-mail, роль, добавочный, статус (активен/заблокирован), последний вход, количество звонков за 30 дней.
- Кнопка «Создать менеджера» → модалка с формой (см. 3.3).
- Действия по строке: редактировать, отправить приглашение повторно, сбросить пароль, деактивировать/активировать.
- Показ ссылки-приглашения с кнопкой «Скопировать» — один раз после создания.

### 5.7. `/admin/analytics` — Аналитика *(только ADMIN)*

Расширенная версия дашборда: сравнение менеджеров по периодам, распределение нагрузки по часам и дням недели, воронка результатов, доля пропущенных по времени суток.

### 5.8. `/admin/telephony` — Телефония *(только ADMIN)*

- Текущий провайдер: `mock` / `exolve`, статус подключения.
- Поля настроек Exolve (API key, номер, секрет вебхука) — вводятся через UI, сохраняются **зашифрованными** в `Setting` (AES-256-GCM, ключ шифрования из `.env`), либо только через `.env` — выбрать вариант с `.env` как основной, UI показывает состояние «настроено / не настроено» без раскрытия значений.
- URL вебхука, который нужно указать в личном кабинете Exolve, с кнопкой «Скопировать».
- Кнопка «Проверить соединение».
- Правила распределения входящих звонков на менеджеров (на будущее, в MVP — заглушка с пометкой).
- Кнопка «Сгенерировать тестовый звонок» (работает при `mock`) — для демонстрации realtime.

### 5.9. `/admin/audit` — Аудит *(только ADMIN)*

Лента действий: кто, что, когда, с какого IP. Фильтр по пользователю и типу действия.

### 5.10. `/profile`

Имя, телефон, тема, часовой пояс, смена пароля.

## 6. Realtime

Требование заказчика: как только звонок завершён — он должен появиться в CRM без перезагрузки.

**Схема:**

1. Событие звонка приходит на `POST /api/webhooks/[provider]` (или генерируется mock-провайдером).
2. Обработчик пишет/обновляет запись `Call` в БД.
3. Postgres-триггер на `Call` (INSERT/UPDATE) вызывает `pg_notify('call_events', payload)` — payload содержит `id`, `userId`, `status`, тип события. Только идентификаторы, без персональных данных.
4. Next.js держит одно постоянное подключение к Postgres на `LISTEN call_events`.
5. Эндпоинт `GET /api/events/stream` (SSE) раздаёт события подключённым клиентам. **Фильтрация по правам на сервере**: менеджер получает события только по своим звонкам, админ — по всем.
6. Клиент по событию делает точечную инвалидацию TanStack Query (список звонков, KPI дашборда) и показывает подсветку новой строки.

**Требования:**
- Автоматическое переподключение SSE с экспоненциальной задержкой.
- Heartbeat каждые 25 секунд (иначе nginx рвёт соединение).
- В nginx для этого роута: `proxy_buffering off`, `proxy_read_timeout 3600s`.
- Индикатор состояния соединения в шапке.
- При потере соединения и восстановлении — полный рефетч текущего экрана, чтобы не потерять события.
- Уведомление о новом входящем звонке: тост + опционально звук (переключается в профиле, по умолчанию выключен).

## 7. Телефония: адаптер и Exolve

### 7.1. Архитектура

Вся телефония — за интерфейсом. Ни один компонент UI и ни один сервис не знает про Exolve напрямую.

```ts
// lib/telephony/types.ts
export interface TelephonyProvider {
  readonly name: string;

  /** Инициировать исходящий звонок (click-to-call) */
  originate(params: {
    fromExtension: string;
    toNumber: string;
    userId: string;
  }): Promise<{ externalId: string }>;

  /** Проверить подпись входящего вебхука */
  verifyWebhook(req: {
    rawBody: string;
    headers: Record<string, string>;
  }): boolean;

  /** Привести сырой payload провайдера к нашей модели события */
  parseEvent(rawBody: unknown): NormalizedCallEvent | null;

  /** Получить ссылку на запись разговора */
  getRecordingUrl(externalId: string): Promise<string | null>;

  /** Проверка доступности API */
  healthCheck(): Promise<{ ok: boolean; message?: string }>;
}

export type NormalizedCallEvent = {
  externalId: string;
  type: 'ringing' | 'answered' | 'completed' | 'failed';
  direction: 'INBOUND' | 'OUTBOUND';
  status: CallStatus;
  fromNumber: string;
  toNumber: string;
  extension?: string;
  startedAt: Date;
  answeredAt?: Date;
  endedAt?: Date;
  durationSeconds?: number;
  recordingUrl?: string;
  raw: unknown;
};
```

Реализации:

- `lib/telephony/providers/mock.ts` — **делаем сейчас**.
- `lib/telephony/providers/exolve.ts` — **каркас сейчас, наполнение после регистрации заказчика**.

Выбор провайдера: `TELEPHONY_PROVIDER=mock|exolve` в `.env`, фабрика в `lib/telephony/index.ts`.

### 7.2. Mock-провайдер

Нужен, чтобы разработка и демонстрация шли уже сейчас.

- Генератор случайных, но правдоподобных звонков: реальные российские номера-заглушки, распределение по времени суток (пик в 11:00–13:00 и 15:00–18:00), доля пропущенных ~15%, длительность разговора — логнормальное распределение со средним ~2,5 минуты.
- Полный жизненный цикл события: `ringing` → `answered` → `completed`, с реальными паузами, чтобы было видно, как строка меняет статус в живом режиме.
- Скрипт `pnpm seed:calls -- --days=30` — наполняет БД историей за 30 дней по всем менеджерам, чтобы дашборд и аналитика не были пустыми.
- Кнопка «Сгенерировать тестовый звонок» в `/admin/telephony`.
- В качестве записи разговора — короткий локальный тестовый аудиофайл, чтобы плеер был рабочим.

### 7.3. Exolve — каркас

**Реализовать сейчас:**

- Эндпоинт `POST /api/webhooks/exolve`:
  - принимает и сохраняет сырое тело в лог;
  - проверяет подпись (по документации Exolve — заполняется после получения доступа к докам);
  - при `TELEPHONY_PROVIDER != exolve` возвращает `503` с понятным телом;
  - идемпотентность по `externalId` через `upsert`;
  - отвечает `200` быстро, тяжёлую работу (например, скачивание записи) выносит в фоновую задачу.
- Клиент API Exolve с базовым URL, авторизацией по API-ключу, ретраями (3 попытки, экспоненциальная задержка) и таймаутом 10 секунд.
- Сопоставление звонка с менеджером: по добавочному номеру (`User.extension`) из события. Если не сопоставился — звонок сохраняется с `userId = null` и попадает в админскую очередь «Нераспределённые».

**Не реализовывать до получения ключей:** конкретные названия полей payload, точный алгоритм подписи, эндпоинты API. Оставить `// TODO(exolve):` с указанием, что именно нужно уточнить в документации. Собрать все такие места в `docs/EXOLVE_INTEGRATION.md` — чек-лист «что подключить, когда придут ключи».

### 7.4. Транскрибация — задел

- Модель `CallTranscript` создаётся сразу.
- Интерфейс `TranscriptionProvider` с методом `transcribe(recordingUrl): Promise<Transcript>` — объявляется, реализация — заглушка.
- В UI карточки звонка блок транскрипции присутствует в состоянии «недоступно».
- В `docs/` описать, что при подключении понадобится очередь фоновых задач (кандидаты: BullMQ + Redis, либо pg-boss на существующем Postgres — второе предпочтительнее, не тянет новый сервис).

## 8. Инфраструктура и деплой

### 8.1. Данные подключения

Передаются отдельно, вставляются в `.env` на сервере:

```
# .env.example
DATABASE_URL="postgresql://USER:PASSWORD@HOST:5432/DBNAME?schema=public&sslmode=prefer"

NEXTAUTH_URL="https://vin2win.online"
NEXTAUTH_SECRET=""          # openssl rand -base64 32
ENCRYPTION_KEY=""           # 32 байта, для шифрования настроек

SEED_ADMIN_EMAIL=""
SEED_ADMIN_PASSWORD=""

TELEPHONY_PROVIDER="mock"   # mock | exolve
EXOLVE_API_KEY=""
EXOLVE_API_URL=""
EXOLVE_WEBHOOK_SECRET=""
EXOLVE_NUMBER=""

LOG_LEVEL="info"
TZ="Europe/Moscow"
```

PostgreSQL — на **отдельном хосте** (не на VPS с приложением). Значит:
- в `docker-compose.yml` контейнера с БД нет;
- подключение по сети — обязательно проверить, разрешён ли доступ с IP приложения в настройках управляемой БД;
- если провайдер БД поддерживает TLS — включить `sslmode=require`;
- пул соединений Prisma: `connection_limit=10`.

### 8.2. Домен

- Приложение на `https://vin2win.online` (корень домена).
- Отдельно зарезервировать `crm.vin2win.online` как алиас на будущее.
- SSL — Let's Encrypt через certbot, автопродление по cron.
- `www` → редирект на основной домен.

### 8.3. VPS

- Ubuntu 22.04/24.04.
- **Первым делом:** создать non-root пользователя `deploy`, добавить SSH-ключ, отключить парольную аутентификацию и вход root по SSH (`PermitRootLogin no`, `PasswordAuthentication no`), настроить `ufw` (открыты 22, 80, 443), поставить `fail2ban`.
- Docker + docker compose plugin.
- nginx как reverse proxy на хосте (или в компоузе — на усмотрение, но конфиг должен быть в репозитории).
- Логи приложения — в файл с ротацией через logrotate.

### 8.4. Docker

- Многостадийная сборка: `deps` → `builder` → `runner`, `output: 'standalone'` в `next.config`.
- Финальный образ — на `node:22-alpine`, запуск от непривилегированного пользователя.
- `HEALTHCHECK` на `/api/health`.
- `docker-compose.yml` с сервисом `app` и переменными из `.env`.

### 8.5. Деплой и скрипты

```
pnpm dev            # локальная разработка
pnpm build
pnpm db:migrate     # prisma migrate deploy
pnpm db:seed        # первый админ
pnpm seed:calls     # демо-звонки (только не в проде)
pnpm lint
pnpm typecheck
pnpm test
pnpm test:e2e
```

- Скрипт `deploy.sh`: pull → build → `prisma migrate deploy` → перезапуск контейнера с zero-downtime по возможности.
- Бэкап БД: ежедневный `pg_dump` по cron, хранение 14 дней, проверенное восстановление хотя бы один раз.
- `/api/health` — проверяет доступность БД, возвращает версию сборки.

## 10. Критерии приёмки

Проверяются вручную, каждый пункт — «да/нет».

1. Открывается `https://vin2win.online` с валидным SSL.
2. Админ входит своим логином, менеджер — своим. Публичной регистрации нет.
3. Админ создаёт менеджера, менеджер по ссылке задаёт пароль и входит.
4. Менеджер **не видит** звонки другого менеджера — ни в UI, ни при прямом запросе к API с подставленным чужим `userId`.
5. Менеджер не может открыть `/admin/*` — получает 403, а не пустой экран.
6. Обе темы работают на всех экранах, при перезагрузке нет вспышки чужой темы.
7. На экране 375px все экраны пригодны к работе: журнал звонков читается как список карточек, фильтры открываются снизу, ничего не уезжает за край.
8. Нажатие «Сгенерировать тестовый звонок» приводит к появлению звонка в журнале **у нужного менеджера и у админа** без перезагрузки страницы, KPI на дашборде пересчитываются.
9. Статус звонка меняется в живом режиме: дозвон → разговор → завершён.
10. Фильтры и поиск в журнале работают на серверной стороне, пагинация не ломается при смене фильтров.
11. Результат звонка и комментарий сохраняются и переживают перезагрузку.
12. Плеер записи воспроизводит тестовый файл.
13. Действия админа отражаются в аудит-логе.
14. Переключение `TELEPHONY_PROVIDER=exolve` не роняет приложение: экран телефонии честно показывает «не настроено».
15. `pnpm typecheck` и `pnpm lint` проходят без ошибок.
16. Пароли в БД — хеши, в логах секретов нет, `.env` не в репозитории.
17. `pg_dump` по cron отрабатывает, дамп восстанавливается.
