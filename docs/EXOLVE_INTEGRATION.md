## Шаг 1. Взять в личном кабинете Exolve

- [ ] **API-ключ** (токен приложения) → `EXOLVE_API_KEY`
- [ ] **Базовый URL API** → `EXOLVE_API_URL` (по умолчанию `https://api.exolve.ru`)
- [ ] **Номер компании** в формате E.164 → `EXOLVE_NUMBER`
- [ ] **Секрет вебхука** (или схему подписи) → `EXOLVE_WEBHOOK_SECRET`
- [ ] Список **добавочных номеров** сотрудников — их нужно проставить
      менеджерам в CRM (`/admin/users` → поле «Внутренний номер SIP»)

## Шаг 3. Уточнить по документации и поправить код

### 3.1. Имена полей payload

**Файл:** `lib/telephony/providers/exolve.ts`, метод `parseEvent`.

Сейчас поддержаны наиболее вероятные варианты написания (`snake_case` и
`camelCase`) — код разберёт большинство форматов, но проверить надо.

- [ ] Идентификатор звонка: ожидаем `call_id` / `callId` / `id` / `session_id`
- [ ] Тип события: `event` / `event_type` / `status`
- [ ] Номера: `from` / `from_number` / `caller`, `to` / `to_number` / `called`
- [ ] Добавочный: `extension` / `ext` / `operator_id`
- [ ] Метки времени: `started_at` / `answered_at` / `ended_at` (ISO или unix)
- [ ] Длительность: `duration` / `duration_seconds` / `talk_time`
- [ ] Ссылка на запись: `record_url` / `recording_url`
- [ ] Направление: `direction` (или выводится сравнением `from` с нашим номером)

**Как проверить быстро:** сделайте тестовый звонок — сырое тело вебхука
пишется в лог целиком:

```bash
docker compose logs app | grep 'webhook received'
```

### 3.2. Названия событий

**Файл:** тот же, функция `mapEventType`.

Сейчас типы определяются по подстрокам, **в строгом порядке**: сначала
неуспех, потом завершение, потом ответ, потом дозвон. Порядок важен:
`noanswer` содержит `answer`, а `disconnect` содержит `connect` — при другом
порядке неотвеченный звонок попал бы в «разговор». Это покрыто тестом.

- [ ] Сверить реальные названия событий со списком подстрок
- [ ] Проверить, что `BUSY`, `CANCELED`, `FAILED` различаются корректно

### 3.3. Алгоритм подписи

**Файл:** тот же, метод `verifyWebhook`.

Сейчас — сравнение общего секрета из заголовка (`X-Exolve-Signature`,
`X-Signature` или `Authorization: Bearer`) в постоянное время. Это защищает
от посторонних запросов, но **не от повтора** ранее подсмотренного.

- [ ] Уточнить реальный алгоритм. Обычно это HMAC-SHA256 от **сырого тела**
      с секретом, иногда с меткой времени в подписываемой строке
- [ ] Реализовать, добавить проверку «свежести» метки времени (окно ±5 минут)
      — она и закрывает повторы
- [ ] Убедиться, что подпись считается от **необработанного** тела: в коде
      `rawBody` передаётся как строка именно поэтому

### 3.4. Эндпоинты API

**Файл:** тот же.

- [ ] `originate` — путь и тело запроса click-to-call
      (сейчас предполагается `POST /v1/Call/Originate`)
- [ ] `getRecordingUrl` — как получить ссылку на запись

- [ ] Формат авторизации: сейчас `Authorization: Bearer <ключ>`

## Открытые вопросы к заказчику

Их стоит закрыть до включения телефонии.

1. **Click-to-call.** Менеджер нажимает кнопку в CRM и АТС соединяет, или
   менеджеры звонят из софтфона, а CRM только фиксирует? От этого зависит,
   нужен ли `originate` вообще.
2. **Хранение записей.** Держим ссылки на стороне Exolve или скачиваем к себе?
   Второе — это дисковое пространство и вопросы по 152-ФЗ.
3. **Распределение входящих.** Сейчас звонок привязывается по добавочному.
   Нужны ли правила (очередь, группы, перевод) — и какие?
4. **Список результатов звонка.** Текущий набор `CallOutcome` подходит или
   нужны свои формулировки под процесс VIN2WIN?

## Транскрибация — что понадобится

Модель `CallTranscript` создана, интерфейс `TranscriptionProvider` объявлен
(`lib/transcription/index.ts`), в карточке звонка блок присутствует в
состоянии «недоступно». Реализации нет.

Для подключения нужно:

1. **Очередь фоновых задач.** Распознавание идёт минутами — в HTTP-запрос
   его не уместить. Кандидаты:
   - **pg-boss** — очередь поверх уже имеющегося PostgreSQL. **Предпочтительно:**
     не тянет новый сервис, не требует Redis, переживает перезапуск.
   - BullMQ + Redis — мощнее, но это ещё один сервис в эксплуатации.
2. **Провайдер распознавания речи** с поддержкой русского и разделением
   по говорящим (диаризация).
3. **Решение по 152-ФЗ.** Запись разговора и её расшифровка — персональные
   данные. Нужны согласие, срок хранения и порядок удаления.
4. **Воркер:** событие «запись готова» → задача в очередь → скачивание →
   распознавание → запись в `CallTranscript` → `pg_notify` для обновления UI.

Блок в карточке звонка уже размечен под текст с разбивкой по спикерам —
вёрстку менять не придётся.
